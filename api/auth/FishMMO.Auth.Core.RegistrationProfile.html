Remarks

Why one field and not seven. Every field of the create-account message is encrypted under its own sequence number, and the server decrypts them by counting back from the message's last sequence. Seven new fields would have been seven new offsets to keep in step on both sides; one field holding a compact serialisation adds one, and the next detail to be added changes FormatVersion rather than the wire arithmetic.

Format. One version byte, one channels byte, from version 3 one RegistrationOptions byte, then strings in a fixed order — phone, beta code, country, real name, address, referral account, and from version 2 the Discord username — each as a two-byte big-endian length followed by that many bytes of UTF-8. An empty string means "not given". Versions 1 and 2 are still read, so a client one release behind can register. Decoding refuses an unknown version, an unknown option bit, trailing bytes, invalid UTF-8 and any field over its length, so the size of what reaches the server's validator is bounded before it is parsed.

Two-factor is opt-in. EnableTwoFactor asks the server to set up an authenticator on the new account. A version 1 or 2 profile has no options byte and reads as opted in: those clients were written when every account was enrolled, and wait for the setup.

Validation. The database's AccountProfileRules is the authority and the server applies it before the account row is created. TryValidate(out string?) is a client-side mirror of the parts a form needs for immediate feedback; the client does not reference the database assembly. A unit test pins the shared limits to the database's.
