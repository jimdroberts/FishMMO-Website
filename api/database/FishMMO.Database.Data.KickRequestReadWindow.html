Where a game server's poll of the kick requests has got to, and which requests it has already handled, on the database clock. Pure bookkeeping: no database, no network, one poll at a time.

Remarks

Why the database clock. A request is stamped by the database when it is written. The poller's cursor used to be seeded from its own host clock and compared with those stamps: a host running ahead of the database skipped every kick stamped inside the lead, for good. Every instant here comes from the database, through KickRequestPage, and the one local measurement — how long ago the reader started — only ever reaches the database as a duration (FirstReadLookbackSeconds).

Why a window and not a cursor. A request becomes visible when its transaction commits, some time after its stamp: a ban writes its kick inside a longer transaction, stamped at that transaction's start. Two writers can therefore commit in the opposite order to their stamps, and a strict (time, id) cursor that has moved past a stamp before its row committed never sees the row. So the poll reads from Watermark, held CommitWindow behind what it has settled, and skips what it has already handled (SnapshotHandled(out long[], out DateTime[])), as the chat pump does (ChatReadWindow). A kick is acted on exactly once as long as it commits within the window of its stamp.

Why handled is (id, stamp). Requests are upserted per account: kicking an account that already has a row keeps the row's ID and moves its stamp. Keyed on the ID alone, that second kick would be skipped as already handled.

Why a floor. Nothing before the reader's first read is re-read by the window's reach back; the first read itself starts at the moment the reader began watching.

Remarks

A request that could not be handed on, and everything after it, is still owed; a full page says nothing about the requests after its last row. Only a short page with nothing refused has read everything that had committed when the read started.
