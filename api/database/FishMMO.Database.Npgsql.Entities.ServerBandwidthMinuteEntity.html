Remarks

Written by the process it describes, once a minute, as a set. Each login, world and scene server samples its transport's cumulative counters on a 60 second timer and writes the difference since the minute began (ServerBandwidthLedger in the Unity project). The write is INSERT … ON CONFLICT DO UPDATE SET col = EXCLUDED.col, never an addition: a retry after a lost commit reply rewrites the same numbers, and a second sample that lands in the same minute rewrites the minute's running total. An additive upsert would count a retried write twice, which is the failure the idempotency work of 2026-09-25 exists to prevent.

Keyed by InstanceID as well as the server's name. A restart starts its counters from zero in a new process; the instance id keeps the two processes' rows apart, so a restart inside one minute neither overwrites the old process's last minute nor mixes the new one's first minute into it. Summing over instances is the reader's job.

Measured values only. Every counter here was counted by the process: the application bytes by the managed WebTransport socket, the UDP payload bytes and datagram counts by msquic. The bytes on the wire (payload plus 28 bytes of IPv4 and UDP header per datagram) are an estimate and are computed when read, never stored, so a change to the estimate never leaves history wrong. See ServerBandwidthMath.

No foreign key to login_servers, world_servers or scene_servers, and the name is copied as text. Those rows are deleted when a server deregisters; the bandwidth it used must outlive it, or a month's egress total would shrink every time a server was retired. Append-mostly (a minute's row is rewritten only by its own process), so there is no xmin token either, as with admin_audit_log.

Kept 14 days, then rolled into ServerBandwidthHourEntity and deleted, one whole hour at a time, by the Control Panel's rollup job.

Remarks

Not the process's own clock. Rows from every host are compared and summed per minute, and a host whose clock ran a minute fast would file its traffic under the wrong minute. The traffic is the interval that ENDED in this minute; IntervalMs says how long that interval was.

Remarks

About 60 000. More when a sample was deferred (the database was unreachable, so the counters kept accumulating and the next sample carried the whole stretch), and about double when two samples landed in one minute. A rate is always bytes / interval, never bytes / 60.
