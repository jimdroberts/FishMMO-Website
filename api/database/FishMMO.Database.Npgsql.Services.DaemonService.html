Claims the commands waiting for one host.

public Task<DatabaseResult<IReadOnlyList<DaemonCommandData>>> ClaimCommandsAsync(string hostName, string instanceId, int maxCommands, CancellationToken cancellationToken = default)

Parameters

Returns

Task<DatabaseResult<IReadOnlyList<DaemonCommandData>>>

Remarks

Atomic: the rows are marked as this instance's in the same statement that selects them, so two daemons sharing a host name cannot both execute one command, and a daemon that dies mid-command leaves a claimed row somebody can see rather than one that is quietly done twice.

Expired commands are never claimed. A restart carried out twenty minutes after it was asked for — once the operator has moved on and players are back on the server — is worse than one that never happened. The one expired command that can come back is this call's own claim, retaken by a retry after its first reply was lost, with no time left: the caller refuses it and reports that, rather than leaving it claimed with no outcome.

Expiry is judged by the database clock, which stamped the command, and each returned command carries the seconds it had left at the claim (ExpiresInSeconds). The caller re-checks by counting those down on its own monotonic clock (DaemonCommandExpiry), never by comparing ExpiresUtc with its wall clock.

Remarks

Not what the command history is. That records what operators asked for through this panel. This records what the supervisors saw happen on their own — a process that died at three in the morning, the restarts that followed, and whether it came back — none of which anybody asked for and none of which is recorded anywhere else. The current-state row in daemon_apps is overwritten every beat, so a fault that has already been recovered from leaves no trace at all without this.

And it is not process output. No log line, no exception text and nothing else a supervised process wrote reaches here; the rows are derived server-side from two enum values and two integers. Log contents routinely carry connection strings and tokens inside exception messages, and a panel route that relayed them would turn a read-only operator view into a way of reading them out of the machine.
