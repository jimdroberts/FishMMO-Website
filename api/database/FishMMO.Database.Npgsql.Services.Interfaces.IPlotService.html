Reads and writes ownership of authored plots of land.

public interface IPlotService

Remarks

Every method that changes ownership reports how many rows it affected, and the caller is expected to check it. The counts are the only way to tell a claim that succeeded from one that lost a race, and treating zero as success would sell one plot to two players.

When those plots should first fall due.

cancellationToken CancellationToken

Returns

Task<DatabaseResult<int>>

How many plots were given a due date.

Remarks

Land claimed while tax was switched off is stored with no due date, and the sweep only looks at plots that have one. Turning tax on afterwards would therefore never touch any of it: those plots would be free forever, and the difference between a founding player and a later one would be permanent.

Only rows with no date are touched, so this cannot reset a plot that is already being billed — running it repeatedly is safe, which matters because it runs on every scene resolve.

Character-owned only. Guild land is deferred rather than charged until a treasury exists, so giving it a date would only make every sweep pick it up and push it along again.

cancellationToken CancellationToken

Task<DatabaseResult<int>>

The number of plots that did not previously exist.

Remarks

Idempotent, because every scene server hosting a channel of the scene runs it on load and they all describe the same land. Plots that already exist keep the ownership they have — registration must never disturb it, or a restart would evict whoever lives there.

Scoped to one world server. The same scene runs on every world, and registering it unscoped would give them all a single shared row per plot — one player's house appearing as already-owned land to everybody on every other world.

Remarks

The state the plot lands in is the caller's to choose, because releasing is two different events wearing one name. An owner handing the deed back leaves a bare lot; a sweep taking land off somebody who stopped paying leaves a house standing empty, which renders differently and tells a passer-by a different story.

TryAdvanceTaxAsync(long, DateTime, DateTime, CancellationToken)

Moves a plot's tax date forward, if it still holds the date the caller charged against.

Task<DatabaseResult<int>> TryAdvanceTaxAsync(long plotID, DateTime expectedDueUtc, DateTime nextDueUtc, CancellationToken cancellationToken = default)

Parameters

plotID long

The plot being charged.

expectedDueUtc DateTime

The due date the caller read.

nextDueUtc DateTime

The date the next payment falls due.

cancellationToken CancellationToken

Returns

Task<DatabaseResult<int>>

1 when this call advanced it, 0 when somebody else already did.

Remarks

The pin is what makes the tax safe to sweep from every scene server at once. Several may host the same world's scenes, they all see the same plot come due, and only the one whose expected date still matches may charge it — so a period produces one payment rather than one per server.

Called before the money is taken, for the same reason a plot is claimed before it is paid for: winning the right to charge is the contended step, and a caller that loses it must not have taken anything.

TryClaimAsync(long, long, long, DateTime?, int, CancellationToken)

Claims an unowned plot.

Task<DatabaseResult<int>> TryClaimAsync(long plotID, long ownerCharacterID, long ownerGuildID, DateTime? taxDueUtc, int claimedState = 1, CancellationToken cancellationToken = default)

Parameters

plotID long

The plot to claim.

ownerCharacterID long

The claiming character, or zero for a guild claim.

ownerGuildID long

The claiming guild, or zero for a character claim.

taxDueUtc DateTime?

When the first tax payment falls due, or null for untaxed land.

claimedState int

The FishMMO.Shared.PlotState the plot enters, as its underlying integer. Defaults to Building.

cancellationToken CancellationToken

Returns

Task<DatabaseResult<int>>

1 when this call took the plot; 0 when it was already owned, does not exist, or the claiming character already owns one.

Remarks

Exactly one of the two identifiers may be non-zero.

The first tax date and the new state are set by the same statement that takes the plot, so there is no moment where land is owned but untaxed, or owned but still showing as an empty lot. Set separately, a crash in the gap would leave a plot nobody ever has to pay for, or one that every channel draws as available.

A character may hold only one plot. That is asked here and enforced by a partial unique index, because this clause alone cannot stop two simultaneous claims on two scene servers. A caller that gets UNIQUE_VIOLATION back rather than a row count lost that race and should report it the same way it reports zero.
