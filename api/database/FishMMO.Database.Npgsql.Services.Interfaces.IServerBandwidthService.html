What a server process writes about its own bandwidth: server_bandwidth_minute rows.

public interface IServerBandwidthService

Remarks

Separate from IServerBandwidthReportService for the reason IServerBoardService is separate from the per-tier services: a game server talks about itself here and has no business reading every other server's traffic.

The key is decided by the caller, before the write, from the database clock. The process reads FetchDatabaseUtcNowAsync(CancellationToken), truncates it to the minute, and passes finished rows to RecordAsync(int, string, Guid, IReadOnlyList<ServerBandwidthSample>, CancellationToken). The upsert never reads a clock itself: ExecuteWriteAsync retries a lost connection, and a retry that re-read now() could land a second after the minute turned and write the same traffic under the next minute's key, where the SET-upsert no longer protects it.

Remarks

Idempotent: writing the same rows twice leaves the table as writing them once, so the caller may re-send rows whose previous write failed or whose reply was lost. A row for a minute already stored REPLACES it (the row carries the minute's running total), unless its interval is shorter than the stored one — the running total of one minute only grows, so a shorter one is an older write arriving late and is ignored.

Failure cases: VALIDATION_ERROR for a bad kind, name, empty instance id, a duplicate minute in the batch, or a row whose Invalid() says why; otherwise the database's own error.
