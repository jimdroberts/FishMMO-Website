Delayed two-factor reset requests.

public interface ITwoFactorResetRequestService

Remarks

For an account that lost both its authenticator and its recovery codes. A request only takes effect after a waiting period; a normal sign-in cancels it, staff may shorten or cancel it, and completing it removes the old factor without ever counting as passing one. This service records the request's lifecycle only — clearing the account's two-factor columns is the caller's job, and belongs in the same unit of work as CompleteAsync(long, string, CancellationToken).

Remarks

Called by staff, and by the sign-in path whenever the account passes two-factor normally — that proves the owner still has their factor, which is the case the waiting period exists to catch. No pending request is not a failure: the sign-in path calls this unconditionally.

Task<DatabaseResult<bool>>

True when this call completed it; false when it was not completable.

Remarks

One conditional UPDATE, so the checks and the mark cannot be separated: a request cancelled by a normal sign-in a moment earlier cannot then be completed, and two completions cannot both report success.

Completion never satisfies two-factor. The session completing it has proved the password only. The caller removes the old factor and sends the player to enrol a new one; it must not treat the sign-in as having passed a second factor.

RequestAsync(string, TimeSpan, string?, CancellationToken)

Opens a request that takes effect after delay, or returns the one already pending.

Returns

Task<DatabaseResult<TwoFactorResetRequestData>>

Remarks

An existing pending request is returned unchanged: asking again never restarts the clock (which would let an attacker keep the owner's cancellation window open indefinitely) and never shortens it (which would let them ask their way past it). The one-pending-per-account rule is a partial unique index, so two simultaneous requests produce one row and both callers get it.

ShortenAsync(long, DateTime, string, string, CancellationToken)

Brings a pending request's effective time forward.

Task<DatabaseResult> ShortenAsync(long id, DateTime newEffectiveUtc, string shortenedBy, string staffReason, CancellationToken cancellationToken = default)

Parameters

The staff account.

staffReason string

Why. Required, at most 256 characters.

cancellationToken CancellationToken

Cancellation token.

Returns

Task<DatabaseResult>

Remarks

Staff may shorten, never extend: newEffectiveUtc must be earlier than the current effective time. Extending is a cancel plus a new request, so a longer wait always starts from a request the history shows. A time in the past is clamped to now. The reason is required because shortening removes the protection the delay gives.
