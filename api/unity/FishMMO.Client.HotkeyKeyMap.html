Remarks

Previously a static method on the uGUI UIHotkeyBar that named twelve inputs. It is not a rendering concern — it names input bindings — and the UI Toolkit hotkey bar needs it, so it moved out of the uGUI tree rather than being duplicated into it.

Positions. Left and right mouse, then the Hotkey1..Hotkey0 actions of the input asset, drive positions 0 to 11 of whichever bar a press lands on (see HotkeyBarLayout for which). The mouse buttons are read directly, as they always were: they are the attack buttons of the world view, not rows in the Key Bindings tab.

Bar modifiers are created here, at run time. How many bars there are is a game setting (HotkeyBarCount), so the actions cannot be authored into the input asset for every game: one HotbarNModifier per extra bar, plus a page up and page down pair for the paged layout, are added to the Player map when the controls are created — before any map is enabled, and before the saved overrides are applied, so the Key Bindings tab lists and rebinds them like any authored action. A single-bar game adds none.

Defaults, and why not Shift. The second bar's modifier is Ctrl and the third's Alt; neither is bound to anything else. Shift is Sprint, so a Shift bar would fire whenever a sprinting player pressed a number — the overlap this scheme exists to avoid — and the fourth bar onwards start unbound: clickable, and given a key in Options if the player wants one.

Stable binding ids. Saved overrides are matched to bindings by binding id and by nothing else (LoadBindingOverridesFromJson), and a binding added at run time gets a fresh random id every launch unless it is given one. Each binding's id is therefore derived from its action's name, so a rebound modifier is still rebound at the next login.
