Remarks

Smoothing is a longer interval, not an average of short ones. The rate shown is the difference between the newest snapshot and the oldest one still inside SmoothingWindowSeconds, divided by the time between them — the transport's own advice (FishNet.Transporting.WebTransport.TransportTrafficMath.TryComputeRates(in FishNet.Transporting.WebTransport.TransportTrafficSnapshot, in FishNet.Transporting.WebTransport.TransportTrafficSnapshot, out FishNet.Transporting.WebTransport.TransportTrafficRates)). An average of one-second rates would come to the same number with the rounding of every step in it.

A window never spans a change of definition. When a layer's measure changes between two snapshots — the native library starting on the first connect, or a browser's first getStats() answer turning an estimate into a reported figure — the two ends count different things, and the transport refuses to difference them (the layer comes back unavailable). Keeping the older snapshots would leave that layer unknown for the whole window; the window restarts at the new snapshot instead, so the layer is unknown for one sample and then correct. The same happens when two snapshots cannot belong to one process lifetime at all (a backend change, a counter that went backwards).

The graph keeps its gaps. A second whose wire rate could not be computed is stored as NaN and drawn as a break in the line, never as a dip to zero.

Pure: no clock, no Unity object. The overlay feeds it one snapshot a second; tests and the render harness feed it fabricated ones.

Remarks

When no older snapshot lies inside the window — a frame hitch longer than the window, so the previous sample is already too old — the previous snapshot is used anyway: an average over a slightly longer interval is still the truth about that interval, and showing nothing would hide a working connection.
