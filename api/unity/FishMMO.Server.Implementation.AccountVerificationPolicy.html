Class AccountVerificationPolicy

Single source of truth for whether, and on which channels, new accounts must prove their contact details: the development-only AutoVerifyAccounts bypass and the per-channel VerifyEmail / VerifySms / VerifyDiscord switches. Which codes an account is then sent and asked for is AccountVerificationRules, shared with the Control Panel.

Two call sites must agree on these answers:

  • Account creation, which decides which codes to send and whether to verify the account outright.
  • The login lookup, which otherwise rejects an unverified account. Without the login side honouring the same switches, an account created before a switch changed would be asked for a code no server will ever send, or let in without one it still owes.

Precedence, highest first.

  1. AutoVerifyAccounts=true (editor and development builds only): every account is verified at creation and no code is sent.
  2. VerifyEmail / VerifySms / VerifyDiscord say which channels this server sends codes on. When all three are false, every new account is verified at creation through the same database write the bypass uses.
  3. Otherwise a code goes out on each channel the player chose that is switched on and the account can receive, falling back to email; any one code verifies the account, and there is no grace period: sign-in asks for a code until one is entered.

The compile-time guard on IsAutoVerifyEnabled(IServerConfiguration) is deliberate: a production player build ignores that key entirely, so a Development LoginServer.cfg that leaks into a production deployment cannot re-enable the bypass. Consequently the flag also has no effect in a server binary built with the Production working environment — build the server with the Development working environment for local testing. The channel switches have no such guard; a missing or unreadable value counts as true, so a typo verifies more, never less.

None of this decides two-factor. An authenticator is set up when the player opts in at registration, however the account was verified, on the game and the Control Panel alike.

Remarks

A code is stored before it is queued — the other order could deliver a code the database never held — and it is stored live for 24 hours. Sign-in re-issues a code only once the stored one has expired or is missing, and nothing else in the game re-issues one. So a code whose queue insert failed stayed live and undelivered for a day, and the player could not verify at all until it lapsed. Expiring that code now leaves nothing redeemable and makes the very next correct sign-in send a new one.

Best effort and bounded to one write: if it fails as well, the day's wait is what remains, and the log says so. The write is pinned to the code this server stored (IAccountService.ExpireVerifyCodeAsync), so a newer code another server issued in the meantime is left alone; it used to be an unconditional re-write that retired it.
