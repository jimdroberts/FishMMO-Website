Remarks

Why a system rather than a partial of whoever asked. Three paths hand out abilities — the ability crafter, the merchant selling a premade, and (in principle) anything a content author adds next — and all three had their own copy of "construct, learn, persist". Only the item layer had worked out what the copies were missing, which is why InteractableSystem.SendNewItemBroadcast was emptied into CharacterInventorySystem.TryGrantItem and its doc says so. This is the same move for abilities, and it is the fix for the same class of bug.

The bug. Ability(template, events) sets ID = -1 by design — its own doc comment says the database assigns the real id — and nothing ever put that id back. PersistAbilityAsync read IsSuccess and threw away the long the upsert returned, so AbilityController.LearnAbility filed every crafted ability under -1: crafting a second ability from a different template silently replaced the first, and because HotkeyData.UnsetReferenceID is also -1 a hotkey bound to either of them validated against the sentinel. The identity is applied here, before the learn, so the window in which a crafted ability has no key does not exist.

Why the learn is deferred rather than corrected afterwards. The item layer can hand an item a provisional identity and correct it on the wire because an item lives in a slot: it can be locked while unidentified, and the slot re-sent (CharacterInventorySystem.ApplyAssignedIdentities). An ability has no slot — the instance id is its key on the server, in the client's known-ability table, in AbilityActivatedBroadcast, and in every persisted hotkey row. Deferring the grant costs one database round trip inside a request that already waits for its result broadcast, and removes the window entirely.

Remarks

Addressed by the ability's row identity, never by its template. The service's statement matches WHERE id = ?, and a template id would either match nothing — reporting success for a delete that removed no row — or, on a table with several rows per template, remove the wrong one.

The guard is held until the delete lands, not until this handler returns. A second forget arriving in that window would otherwise read the same live ability and delete the same row twice, and a re-craft arriving in it would see a character that still knows the ability.

Returns

bool

true when the grant was admitted; false when it was refused outright.

Remarks

Asynchronous by contract. A true return means the request was admitted, not that the ability exists yet. Exactly one of onGranted or onFailed runs later, on the main thread, once the database has answered.

This method takes ownership of releaseGuard. It is invoked exactly once on whichever path finishes the request — a synchronous refusal, a refused enqueue, or the persist's continuation — so a caller must NOT also release it, and a caller that holds a request-open guard across this call passes the release in here instead of running it in its own finally.

A refusal is synchronous and already reports itself through the return value, so onFailed is reserved for a persist that was attempted and did not land. Callers answer a false return themselves.

Payment is settled on completion, not before the call. A caller that charges for the ability passes the charge as settle; it runs on the main thread once the row exists and only if the character is still resident, and the ability is learned strictly after it returns true. If the character has left, or settle returns false, the row is revoked and nothing is learned, announced or owed. Charging before the call was how a persist that failed after the player left became an unrefundable loss. A false from settle means the caller has already answered the player; neither onGranted nor onFailed runs for it.
