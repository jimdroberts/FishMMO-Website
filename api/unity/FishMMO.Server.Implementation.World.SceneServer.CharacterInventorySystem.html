Remarks

The vacated slot is the whole reason this overload exists. Item rows are keyed (character_id, slot), so a move onto an EMPTY slot writes the item at its new index and leaves the row at the old index untouched — the same item persisted twice. Only the write side was emitted here before, because affectedItems collects non-null items and a move-to-empty produces exactly one of them, which reads like a complete description of the change and is not.

The 60-second snapshot prunes the stale row, so this never survived a clean shutdown — but "duplicated until the next snapshot, permanently if the scene server dies first" is not a guarantee worth relying on when the delete costs one list entry.

TryGrantItem(IPlayerCharacter, Item, InventoryType)

Grants an item to one of a character's containers: places it, tells the owning client, persists it, and hands it the identity the database assigns.

public bool TryGrantItem(IPlayerCharacter character, Item item, InventoryType container)

Parameters

character IPlayerCharacter

The character receiving the item.

item Item

The item. May be merged into stacks the character already holds.

container InventoryType

Which container receives it.

Returns

bool

True when the whole item was placed.

Remarks

THE grant path. Every server-side source of a new item — pickups, corpse and chest loot, merchant purchases, mail, quest and achievement rewards, the ECA give action — comes through here, because it is the only path that completes an item: a fresh item has no database identity, and until its first write returns one it cannot be equipped (the attribute ledger declines an id of zero), used, moved, or safely written a second time. The slot it lands in stays locked until that identity arrives; see TryPersistGrantedItems(IPlayerCharacter, List<Item>, InventoryType, string).

All-or-nothing on the container: the whole stack fits or nothing is placed, so a caller that reserved the item elsewhere (took it off a corpse, charged for it) can put it back on a false return.

TryRunExchange(IPlayerCharacter, IPlayerCharacter, Func<ItemExchangeLeg[]>, Action<bool>, string)

Runs a two-character exchange — a completed player trade — as ONE database transaction whose commit is the point of truth, so a crash at any instant leaves the database holding either the whole trade or none of it, and memory never diverges from that in a direction that duplicates anything.

public bool TryRunExchange(IPlayerCharacter first, IPlayerCharacter second, Func<ItemExchangeLeg[]> applyOnMainThread, Action<bool> onFinished, string operation)

Parameters

first IPlayerCharacter

One party.

second IPlayerCharacter

The other party.

applyOnMainThread Func<ItemExchangeLeg[]>

Called on the main thread while both row locks are held. Returns the two legs (first's then second's) after mutating memory, or null to abort before anything was mutated.

onFinished Action<bool>

Called on the main thread once, with true when the transaction committed and false when it was aborted or rolled back. Only called with false after a null apply, or with the memory mutation still in place and every touched slot already unlocked, so the caller can undo it.

operation string

Short operation name used in persistence log lines.

Returns

bool

True when the exchange was accepted for execution. False means nothing will run and nothing was changed.

Remarks

THE PROTOCOL, in order, because the order is the guarantee:

  1. Worker: open the transaction and take BOTH characters' session row locks, in ascending id order. From here no other write for either character can commit until this transaction ends: every write takes the same lock.
  2. Main thread, while the locks are held: applyOnMainThread re-validates and mutates memory (or returns null to abort with nothing changed), and the resulting rows are captured with their journal sequences and versions stamped NOW. Every write captured before this instant therefore carries a lower sequence and lower versions than the trade; every write captured after carries the trade's content. The slots in TouchedSlots are locked until the outcome is known.
  3. Worker: write both characters' rows and the ledger, commit.
  4. Main thread: unlock, then onFinished(true). On any refusal: roll back, unlock, onFinished(false) — the caller undoes its memory mutation exactly, which the locks make possible — then every write captured from memory while the exchange was applied is VOIDED in the journal, because its content described a trade that never happened, and both characters are reconciled from the restored memory.

Crash analysis: before the commit, memory is lost and the database rolls back — the trade never happened for either side. After the commit, the database holds the whole trade for both. A write captured before the apply that lands after the commit is older by sequence and version and is refused. There is no interleaving in which one character's half is durable and the other's is not.
