Class EquipmentController

Namespace
FishMMO.Shared

Controls the character's equipment slots, handling equip/unequip logic and network synchronization.

Implements IPredictableController at Order 93 so equipment participates in the prediction pipeline: an owner's equip or unequip is INPUT, carried by EquipmentRequest, applied by both the owner and the server inside the replicate body for that tick, and confirmed by the reconcile. Equipment-driven attribute changes therefore land on the same tick on both peers, and the attribute reconcile (Order 95) never has a socket to correct that the replay would not also have re-applied.

Three network paths feed this container and they must agree with one another:

  • The spawn payload (WritePayload(NetworkConnection, Writer)/ReadPayload(NetworkConnection, Reader)) — owner shaped for the owner, template+seed only for everyone else.
  • The owner's replicate input and reconcile snapshot: the input moves items, the snapshot says which instance sits in each socket, and RestoreFromReconcile(EquipmentReconcileEntry[], uint) settles any disagreement by MOVING the real instance, never by cloning it. A reconcile that predates a request restores the earlier state and the replay re-applies the request.
  • EquipmentObservedSlotBroadcast, sent by the server to the character's observers after every successful equip/unequip, applied by ApplyObservedSlot(int, int, int).

ServerRequestValidator

Server-side gate consulted before a replicated request is applied: is this character allowed to act at all, and may it reach the named container right now?

public static Func<ICharacter, InventoryType, bool> ServerRequestValidator

Field Value

Func<ICharacter, InventoryType, bool>

Remarks

Installed by the server's inventory system. It answers the two questions this shared class cannot — "can the character act" is a server-side validation rule set, and "is a banker in range" needs the scene object registry. Null on every other peer, and null on the server means no gate, which is the permissive default a test harness expects.

Order

Execution order in the unified prediction pipeline. Runs after CooldownController (90) and before CharacterAttributeController (95) so equipment attribute modifiers are settled before the attribute reconcile snapshot.

public int Order { get; }

Property Value

int

Remarks

Must stay below Order (95). Restoring an item restates its own ledger entry through ItemGenerator.ApplyAttributes → CharacterAttribute.SetSource; the attribute reconcile then installs the server's total as the residual over whatever those entries sum to. Raising this above 95 would have that residual computed before this tick's equipment is settled, so an item equipped on the reconciled tick counts twice. See the remarks on Order.

RequestEquip(Item, int, InventoryType, ItemSlot)

Queues an equip to be applied on the owner's next replicate tick.

public bool RequestEquip(Item item, int sourceIndex, InventoryType fromContainer, ItemSlot socket)

Parameters

item Item

The item to equip, as the caller currently sees it.

sourceIndex int

Its index in fromContainer.

fromContainer InventoryType

The container it is in.

socket ItemSlot

The equipment socket it is going to.

Returns

bool

True when the request was queued.

Remarks

Owner only. Validates what can be validated locally — the item is where the request says, it fits the socket, it has a database identity, neither slot is locked — and refuses without queueing when it cannot. One request is held at a time; a second call before the first has ridden a replicate replaces it, and the displaced request is reported through OnRequestResolved as not applied.

ResetState(bool)

Drops the per-spawn container state before the object returns to the pool.

public override void ResetState(bool asServer)

Parameters

asServer bool

True if called on the server.

Remarks

The locks are the reason this exists. A slot is locked for the duration of an operation — a consumable activation, an equip round trip — and unlocked when that operation resolves. A despawn mid-flight resolves nothing, so the lock was still set when the object went into the pool, and OnDestroying was the only thing that cleared it: a path a pooled object never takes. The next character to occupy the slot inherited a permanently locked inventory slot, which IsSlotLocked(int) makes unswappable, unremovable and untransferable for the rest of that character's session, with nothing in the UI to explain it.

The subscriber lists go with them. Both events are held by client panels bound to the character that is being torn down; leaving them attached to a recycled container would drive the previous occupant's UI from the next occupant's slot writes.

Items are deliberately NOT cleared here. Each concrete container clears its own in its ResetState, and EquipmentController has to run work either side of that call — see its override for why the order there cannot be inverted.

OnRequestResolved

Fired on the owner when a queued request has run in the replicate body, whether or not it was applied. Arguments: the kind, the socket, the container the request named, the container index (or -1 for an unequip), and whether the move happened.

public event Action<EquipmentRequestKind, ItemSlot, InventoryType, int, bool> OnRequestResolved

Event Type

Action<EquipmentRequestKind, ItemSlot, InventoryType, int, bool>

Remarks

This is how a panel that marked two slots as waiting learns that nothing will change them. A refusal here is LOCAL — the item was no longer where the request said, or the socket did not fit it. A refusal by the SERVER is not reported through this event at all: it arrives as a reconcile that puts the item back, which updates the slots directly.
