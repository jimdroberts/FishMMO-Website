Remarks

The closed pose is wherever the moved transform sits when the scene loads, so a designer places the door shut and describes only the offset that opens it. Offsets are local to the moved transform's parent, so a door rotated to fit a wall opens along its own axis rather than a world one.

The motion is worked out in Update on both peers rather than replicated per-frame. Only the switch's state crosses the wire — once, when it changes — with the server tick the change began at and how far along the travel it stood then (ITimedSwitchTarget). Every peer evaluates the same pose from FishNet's synchronised tick, so the door stands in the same place on every screen and on the server, whose collider the character controller tests. It used to start on each peer when that peer heard of the change (a round trip apart), run on its own frame times, and snap a late arrival to the end pose while the server was still mid-swing.

The server moves too, and must: this transform carries the collider the character controller tests against, so a door that only opened on clients would be an invisible wall.

Remarks

Each FishMMO.Shared.SwitchTargetMover.solidWhenClosed collider is placed where that pose puts it, and every character collider near it is tested against it there (ComputePenetration(Collider, Vector3, Quaternion, Collider, Vector3, Quaternion, out Vector3, out float) takes both poses, so the leaf is never moved to ask). The broad phase is a sphere round the posed collider with slack for transforms physics has not synced yet; the test itself reads the transforms.

Remarks

Blocking or not, and when blocking, in the resting pose the controller collides with. Applied by TickPoser before every live and replayed tick, at the server tick that tick runs at. Before it, a door's collider turned solid or passable on the client's FRAME estimate of the server tick, which is not the tick the owner's prediction runs at and was never rewound for a replay, so walking through a door as it opened or shut was corrected.

Remarks

For catching up rather than for reacting. A client that starts observing a switch reads the switch's current state out of its spawn payload, and that state describes something that happened before the player arrived — possibly hours before. Replaying it through Activate(IPlayerCharacter) would play the transition too, so walking into a room would set every door in it swinging. Nothing on the interaction path calls this.
