Remarks

Why a bit set. A scene has tens of waypoints, every character eventually unlocks most of them, and the whole set is read and written together: on login, in the spawn payload, and on save. One row per (character, waypoint) would be a forty-byte row for a single bit; the set stores those bits as bits. The same shape is on the wire and in the database (character_waypoints, one row per non-empty page), so nothing translates between representations — see CharacterDialogueChoiceData for the precedent.

Why pages. A single 64-bit word would cap a scene at 64 waypoints, and the day that cap is hit is the day a designer's sixty-fifth waypoint silently fails to persist. Pages make the set unbounded (to MaxIndex, a sanity cap on authoring rather than on storage) at the cost of one extra small integer per row.

Persistence without a version. Bits are only ever set, and the database merge is an OR. So "what still needs writing" is exactly unlocked & ~persisted, and confirming a write is persisted |= written; a bit set while a write was in flight is not in written and stays dirty. No counter to bump and no stale-confirmation hazard — the trap the versioned tables fell into (see the attribute/ability persistence notes).

Remarks

OR-ed in, never assigned. A restore arriving after an unlock in the same session (a slow load racing a quick interaction) must not drop the unlock; and on the owner client the payload may be re-read on a pooled respawn.
