Remarks

Two clocks, and they are not the same one. The weather timeline is anchored in the SYNCHRONISED tick (TimeManager.Tick): WeatherTimeline.WorldSecondsAt measures from WorldSecondsTick, which the scene server stamps from its own TimeManager.Tick and broadcasts. A replicate's input.GetTick(), however, is the OWNING CLIENT's unsynchronised LocalTick — a counter that restarts at zero on every connect — so on the server the two differ by an arbitrary per-connection constant. Feeding an input tick straight to the weather would read the forecast for some other hour entirely, and would read a DIFFERENT wrong hour on the client than on the server, so the reconcile would fight the prediction for ever.

The mapping. FishNet hands us the pairing it reconciled on: ClientStateTick is the local tick of the last reconcile and ServerStateTick is the server tick of that same reconcile. The difference between them is the constant, so

FishNet 4.7 publishes that pairing only WHILE it reconciles — PredictionManager resets both to UNSET_TICK after every reconcile, where 4.6 left them standing until the next. Read raw, live prediction would then fall back to the client's synchronised estimate while replay used the pairing, and the two would disagree by however far the estimate is off. So WeatherExposureTick.ReconcilePairing remembers the pairing of the last reconcile per PredictionManager (from OnPreReconcile), and live prediction and replay read the same numbers again. It is forgotten when the client connection stops, because LocalTick restarts. 

weatherTick = ServerStateTick + (inputTick − ClientStateTick)

and this one line is correct both live and in replay. In replay it is provably so: FishNet walks ClientReplayTick and ServerReplayTick forward together from ClientStateTick + 1 and ServerStateTick + 1 (PredictionManager, the while (ClientReplayTick < localTick) loop), so for the replicate being replayed at client tick t the server's tick is exactly what the formula returns. That identity is what Resolve(bool, uint, uint, uint, uint, uint) asserts against when a replay tick is supplied, and what the closed-loop tests pin.

On the server the input tick is not used at all. The server IS the authority on when "now" is; its own TimeManager.Tick is the weather's tick, and the client's counter is only a label for matching inputs to reconciles.

Pure arithmetic on purpose: everything here takes plain numbers, so the whole mapping can be tested without a NetworkManager, a connection or a running scene.

Remarks

Not used by the controller. Taking the replay counter directly would work, but it is only valid inside a replay, so the controller would need two code paths where one will do — and a second path is a second thing to get wrong.

A tick in the weather timeline's (synchronised) domain. Zero is a real answer — it is the first tick of the timeline, which is where a mapping that would fall below it is clamped — and is also what Unset happens to be, since FishNet's sentinel is literally zero. Nothing downstream needs to tell the two apart: both mean "read the oldest weather".
