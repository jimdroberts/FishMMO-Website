Remarks

Who simulates. The server and the owning client, driven from CharacterPredictionController's single [Replicate] like every other controller. An observer never runs it: state forwarding is off on every prefab, and the buffs it applies reach observers the way all buffs do.

Why it can be predicted at all. Everything it reads is a pure function of the tick and the position. The weather timeline is deterministic from its seed and clock anchor, both of which the client already holds; shelter is a point-in-collider test (WeatherVolume.Contains, and so RegionGeometry.ContainsPoint) rather than a physics trigger, which matters because triggers poll in OnPostPhysicsSimulation, outside the replicate, are not rolled back, and re-fire their Enter/Exit on every replay (N12). So the owner can work out the same answer the server will, and a replay of the same tick gives the same answer again.

Which clock. The weather is evaluated at a SYNCHRONISED tick, and the replicate's tick is the owner's unsynchronised counter: see WeatherExposureTick, which is where that conversion lives and is tested.

No new field in the input. Nothing is sent up from the client; the whole step is derived from the tick, the character's own position and the timeline both sides already have (N12). What does ride the reconcile is the levels, because they are timers — see Exposure.

RestoreFromReconcile(ExposureReconcileEntry[])

Takes the server's levels as the truth, and re-derives which buffs are held.

public void RestoreFromReconcile(ExposureReconcileEntry[] entries)

Parameters

entries ExposureReconcileEntry[]

Remarks

The held set is rebuilt from the restored levels rather than carried across the reconcile, because the levels have just been overwritten: a buff whose level the server says never reached the threshold must not still be marked as held, or it would never be applied again. Dequantising here — the same function the server quantised with — leaves both peers on bit-identical levels, so the replay that follows starts from the server's state exactly.

RestoreFromReconcile(ExposureReconcileEntry[], BuffReconcileEntry[])

RestoreFromReconcile(ExposureReconcileEntry[]), with the server's buffs for the same tick: they say which side of a hysteresis band a state or a recipe was on, which the levels alone cannot.

public void RestoreFromReconcile(ExposureReconcileEntry[] entries, BuffReconcileEntry[] serverBuffs)

Parameters

entries ExposureReconcileEntry[]
serverBuffs BuffReconcileEntry[]

Remarks

Inside the band (between release and apply) "held" depends on which way the level was travelling. The server's answer is in the same correction: the buff is on its list or it is not. Without it a state in the band kept whatever this client last believed, and every recipe was read as NOT held, so a buff the server was holding by its release margin was taken off by the owner at its next sample, put back by the next correction, and taken off again by the replay: an icon and an effect flickering once a second.
