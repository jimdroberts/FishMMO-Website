Remarks

A failed result is one of three different things, and the panel used to answer all three the same way — a 400 carrying ErrorMessage:

  • Not found. The row the request named does not exist. A 404, with the caller's own wording, because "no such account" is a sentence the page already knows how to say.
  • A refusal. The service said no: a value out of range, a ticket above the actor's tier, a stale version, a code that does not redeem. The message was written by the service to be read, and it is passed through as a 400 exactly as before.
  • A fault. The database failed: a dropped connection, a timeout, a statement that threw. Its message is built from the underlying exception (BaseService.MapFinalException) and can carry a host, a port or a column name, which is nobody's business in a browser — and a 400 told the browser the request was wrong, when trying it again was the right thing to do. A 503 with the caller's own wording, and the real message goes to the log, where it is useful.

A controller that treats a particular code specially (a 409 for a stale edit, a named collision) still does so before calling this. This is the answer for everything else.

Remarks

Every code here carries a message that was either written by a service for its reader or is one of the fixed, safe sentences the base service maps a constraint violation to. INVALID_ARGUMENT and INVALID_OPERATION are deliberately absent: they are built from framework exception text, including EF's inner exceptions.
