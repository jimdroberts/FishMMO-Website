Remarks

The two paths must not drift: an account created on the web and an account created in the game client have to be indistinguishable afterwards, or a player who registered on one and signed in on the other would find their 2FA missing, their verification never sent, or their salt and verifier shaped differently.

The sequence mirrored from AccountCreationSystem.ProcessAccountCreationAsync, with the panel's additions marked:

  1. Validate the username against IsAllowedUsername(string).
  2. Bound the salt and verifier lengths (256 / 1024).
  3. (panel) Validate the optional profile with TryValidate(AccountProfileData, out AccountProfileData, out string).
  4. (panel) With the beta gate on, or a code given, check the code is redeemable — BEFORE the account exists.
  5. Persist the account with IAccountService.PersistAsync.
  6. (panel) Persist the profile and chosen channels, then redeem the beta code.
  7. Auto-verify when the development policy says so or the server verifies nothing; otherwise send a code on every channel Effective(AccountVerificationChannels, AccountVerificationChannels, AccountVerificationChannels) names, or verify without one when it names none.
  8. Only when the player opted in to two-factor: generate a TOTP secret, encrypt it under the deployment master KEK, persist it, then enable TOTP.
  9. With it, generate recovery codes, hash them, persist them. (panel) The secret, the enable and the codes are one transaction — see EnrolAsync(string, bool, CancellationToken).
  10. Return the otpauth URI and the plaintext recovery codes once (none without the opt-in).

Everything after the account row exists is best effort, as it is in game: a follow-on step that fails is logged, and the account is kept rather than a half-made registration being reported as a failure the player then retries into "that name is taken".

Remarks

The password is never a parameter here, and there is nowhere for it to arrive: the browser derives the salt and verifier with the same SRP rules the game client uses and sends only those, so this service could not log or leak a password if it tried.

Remarks

Returns nothing, deliberately. The endpoint is anonymous and answers identically whatever happens here — unknown account, verified account, a channel it never chose, a cooldown still running — or it would say which names exist and what they chose.

A code still waiting in the queue is not replaced: generating a new one would invalidate the code in the message that is about to arrive.

Email and SMS only. The Discord code is delivered once, as one DM, and is never replaced — a second code would strand the first DM, and the bot never sends another — so the endpoint refuses a Discord resend before it gets here.

Remarks

PersistVerifiedByCodeAsync matches the code against every code the account holds — email, SMS and Discord — and checks the expiry, in one statement. Any one match verifies the account outright; there is no second code to ask for afterwards.

Every wrong code is counted through RecordAsync(IAccountService, ISupportTicketService?, string, CancellationToken), in the database the login server counts into, and the third in a row opens a support ticket. What that did is logged and never returned: the answer is InvalidCodeError whatever happened, so the endpoint cannot be used to learn anything about an account.

A wrong code, an unknown account and a verified one all come back from the service as the same VALIDATION_ERROR, so counting only that keeps every one of them identical. A database fault is not a wrong code: it used to be counted as one, so a correct code typed during an outage was told it was invalid and moved the account towards an automatic ticket. It is answered with "try again" instead — the same for every account, so it says nothing either.
