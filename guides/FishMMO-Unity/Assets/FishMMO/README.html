Assets/FishMMO

View this file on GitHub

All of FishMMO's own code lives here. The core is what every game needs: log in, create a character, enter a world scene, move, fight, save. A module is a feature a game may leave out: delete its folder and the game still compiles, builds and runs.

Layout

Folder Assemblies Holds
Core/ FishMMO.Core The engine-free runtime: entities, systems, stats, effects, tags, and the module catalogue. References nothing but the .NET base library.
Shared/ FishMMO.Shared (+ editor assemblies) Everything both peers run: characters and their controllers, prediction, abilities, items, NPCs, interactables, templates, broadcasts, world scene data, the editor dashboard.
Client/ FishMMO.Client (+ editor assemblies) The game client: launcher, login, connection, UI Toolkit windows and HUD, input, settings, rendering.
Server/ FishMMO.Server The Login, World and Scene servers: the server core contracts and their implementation.
Editor/ FishMMO.GeneratedFiles.Editor, FishMMO.MockContent.Editor, FishMMO.AbilityContent.Editor, FishMMO.Render.Scratch Editor-only content tools that are not part of a module.
Tests/ FishMMO.UnitTests, FishMMO.UnitTests.PlayMode, FishMMO.TestHarness* The core's tests and the test harness (simulation scenes, the Core Gate world).
Shaders/ The core's shader library: the lit surface stack, the light table, shadow caching, culling and instancing includes.
Modules/ FishMMO.<Module> and its side assemblies The optional features.

Scenes, prefabs, templates, materials and settings that are not part of a module stay where they were, under Assets/Scenes, Assets/Prefabs, Assets/Templates and so on.

Classes keep their namespaces (FishMMO.Shared, FishMMO.Server.*, FishMMO.Client) when they move into a module. The assembly is the boundary, and scenes, prefabs and assets keep resolving their scripts.

A module's folder

Assets/FishMMO/Modules/<Name>/
├── Runtime/    FishMMO.<Name>          Both peers: data, broadcasts, character parts, the GameModule declaration
├── Server/     FishMMO.<Name>.Server   Server systems (ServerBehaviour assets), persistence participants
├── Client/     FishMMO.<Name>.Client   Windows (prefab, UXML, USS) and client hooks; constrained to !UNITY_SERVER
├── Editor/     FishMMO.<Name>.Editor   Dashboard pages and tools; Editor/RenderScratch holds the panel renders
├── Tests/      FishMMO.<Name>.Tests    EditMode tests, including wiring tests for every seam the module uses
├── Templates/                          The module's ScriptableObject content
└── README.md

A module has only the folders it needs. The server assembly is limited to the Editor and the dedicated-server platforms; the client assembly is constrained to !UNITY_SERVER.

How a module plugs in

The core never names a module. A module reaches the game through seams the core exposes, and each module's README lists the ones it uses.

Seam Where What it does
[assembly: GameModule(typeof(X))] Core Lists the module among the installed modules (ModuleCatalog). Its Install may add systems, archetype components and effects to the Core world.
[assembly: CharacterPart(typeof(X))] Shared, CharacterPart.cs Adds a controller to every character at wake. No prefab carries it; its state rides the character's spawn payload.
[assembly: CharacterPersistence(typeof(X))] Server, CharacterPersistence.cs A participant in the character's load and save, over the module's own tables.
[assembly: CharacterCreationContributor(typeof(X))] Server, Login server Adds rows when a character is created.
[assembly: HarmRelation(typeof(X))] Shared, Relations/HarmRule.cs A relation in the rule that decides who may harm whom.
[assembly: OperatorCommandProvider(typeof(X))] Server, OperatorCommandContracts.cs Adds /gm and /admin commands (hosted by the Staff module).
Addressables label SceneServer_Systems Server.AdoptModuleSystems A ServerBehaviour asset with this label is adopted by the scene server at start.
Addressables label ClientWorldGUI_Panels ModulePanelHost A window prefab with this label is placed into ClientWorldGUI when that scene loads.
GameMenuEntries, CharacterMenuEntries Client Entries in the game menu and in character right-click menus.
ClientServices, SceneServerModuleServices Client, Server Services started with the client or the scene server.
ModuleRenderFeatures Client, FishModulePassesFeature Render passes hosted by the core renderer feature on the three URP renderers.
ServerPreloadLabels Shared, Bootstrap Addressables labels the server loads at start.
[DashboardTool], [assembly: DashboardPage], DashboardFullPages Editor dashboard Buttons and pages in the FishMMO Dashboard.

What a removed module leaves behind:

  • Database tables and rows stay in place, unused. There is one schema; nothing is dropped.
  • Scene objects that belong to the world (plots, waypoints, dungeon entrances, merchants) stay in the scenes. Without the module they do nothing when used.
  • Scripts in world scenes that point into the module show as missing scripts. The asset audit accepts these only while the module is removed (see below).

Removing a module (the gate)

Every module was checked by removing it. To repeat the check:

  1. Snapshot Assets/AddressableAssetsData/AssetGroups/*.asset and Assets/AddressableAssetsData/link.xml. When Unity saves, it deletes the removed module's entries from the groups, and every batch run rewrites link.xml.
  2. Record the removed GUIDs. Write the GUID of every .meta file in the folders being removed, one per line, to Library/FishMMOGate/RemovedGuids.txt (or to a file named by the FISHMMO_GATE_REMOVED_GUIDS environment variable). AssetReferenceAuditTests then accepts world scenes' missing scripts and dangling references into those modules.
  3. Move the module's folder and its .meta out of Assets, together with every module in its "Remove together with" column.
  4. Run the EditMode tests in batch mode with the editor closed: Unity -batchmode -projectPath FishMMO-Unity -runTests -testPlatform EditMode -testResults <file>. Expect no compile errors and no failures beyond the known ones. If a server build ran last, add -buildTarget Linux64 -standaloneBuildSubtarget Player, or the run finds no tests.
  5. Restore the folders, the groups and link.xml, and delete RemovedGuids.txt.

The Phase 4 gate went further: with all seven world modules removed, a client and a server were built and a new character logged into the Core Gate world (Tests/TestHarness/Editor/CoreGateSceneGenerator.cs), lit and shadowed (2026-11-18).

Writing a module README

Each module README follows one template: a short description, a facts table (module id, assemblies, depends on, depended on by, remove together with), the folders, the core seams it uses, what stays in the core, removing it, and then any feature reference.
